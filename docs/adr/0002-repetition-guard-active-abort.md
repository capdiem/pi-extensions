# 复读防护扩展采用主动打断（abort + steer），限定于本扩展范围

Status: accepted

ADR 0001 为 `ask_user` 触发问题确立了「纯工具元数据优先、不做主动注入」的哲学。`pi-repetition-guard`（复读防护扩展）是**另一类问题**：它检测 LLM 流式输出中的复读循环（thinking-runaway / 万字复读）并**主动中止**——通过 `message_update` 观测、`ctx.abort()` 中止当前生成、`sendUserMessage(steer)` 注入纠正并重跑。这是超出 ADR 0001 范围的主动干预，属于本扩展的特权边界。

## 为什么不矛盾

- ADR 0001 针对的是**工具发现性/触发可靠性**问题——那里被质疑掉的是「主动注入 + 生命周期」的复杂度，元数据优先是正确取舍。
- 复读防护是**安全机制**：主动打断正是它的全部意义。设计访谈中用户在明确权衡 ADR 0001 哲学后，仍选择了「主动打断」而非「仅检测」。
- ADR 0001 的「不做主动注入」仍然有效，但**范围限定在 ask_user 触发场景**。后续扩展应参照本 ADR 的边界判断，而非假设「仓库一律不注入」。

## 降误伤设计

主动打断有误杀正常长篇/含天然重复内容的风险，用以下手段约束：

- **单一证据触发（v2 修订）**：仅当尾部出现「≥2 个逐字精确副本的连续周期」（tape-loop）才触发。**两段式 stage-1 已被废弃**——实测表明所有早期预警信号（shingle 新颖度、块重复、分数倍周期）都会在正常的长结构化思考上误报，只有精确连续周期是干净的。详见 CONTEXT.md 触发策略。
- **v5 修订（变体循环）**：实测发现用户场景存在"近似变体循环"（如 b80c3738："Let me read L1000-1035" 换词反复），精确周期抓不到。新增**短片段近重复主导度**信号（消息内 ≤100 字符的片段中 ≥90% 互为近重复，5-gram 重叠 ≥0.7），与精确周期 **OR**。关键：只统计**短片段**——这把它与"合法长模板化思考"分开（后者由长段落构成、几乎没有短片段，实测 0 误报）。严格单消息内部，不做跨消息比较。
- **重试预算 2 次**：措辞逐级升级（1→2），末次给出"放弃或说明卡点"的明确兜底，防止扩展自己陷入 abort↔steer 死循环。
- **斜杠命令 `/runaway` 开关**：默认开启，但护栏只能由用户关闭（LLM 无法关掉自己的防护）。
- **steer 带重复样例**：把截断的重复块回喂给模型，是最有效的跳出信号。

## 不变项

- `message_update` 中流改写仍不可用（ADR 0001 属实）——本扩展不改写，而是中止+重跑。
- Pi 无内置 `repetition_penalty` / `no_repeat_ngram_size`——检测完全在扩展侧做启发式。

## Consequences

- 被中止的复读文本会残留在历史与后续上下文中（用户选择不做 `message_end` 清理）；steer 重跑是全新回合，能看到自己的垃圾 + 纠正指令，因此不阻塞重试。若后续 token 膨胀成问题，可再评估清理。
- 需要轻量诊断记录（hard 触发、重试次数、预算耗尽），支撑阈值调优——与 ADR 0001 的诊断纪律一致。
- **已知局限**：检测要求精确连续循环；轻微漂移的复读（副本间有小改动）会漏检——这是刻意接受的取舍（宽容信号必然误报正常思考）。
- **实测修订记录（v1 → v2）**：v1 的尾部窗口 shingle 新颖度信号在正常长 xhigh 思考上误触发（用户实测「重试两次经常被触发然后退出」的根因）。v2 改为尾部周期检测，实测对正常思考零误报、对真实复读（含长块）仍正确触发。stage-1「疑似」阶段因无可靠早期信号而被移除。
- **实测修订记录（v2 → v3，工具调用循环）**：用户的真实案例是**工具调用循环**（模型反复调用同一工具/同一参数，如连续 `git status`，28 轮不收敛），其文本是近似重复的变化体，**精确周期检测无法命中**。v3 新增 `tool_call` 事件上的工具循环检测（同工具+同规整参数在滑动窗口内 ≥4 次 → 拦截 + 针对性 steer），实测对用户案例在第 4 次调用即拦截。干预层：文字 steer 对工具循环无效，改为 `tool_call` 的 `block` + `terminate` 拦下重复调用。原 grilling 第一轮把「工具调用循环」排除在范围外，此修订将其纳入。
- **实测修订记录（v4，重试与提示词）**：用户实测确认检测已能正常识别重复片段，问题在**干预**——重试后仍卡死然后放弃。v4 将重试预算 2→3，并把 steer 提示词从「给出简洁最终回答」改为**动作导向**（"你陷入循环：反复复述动作却不执行，请直接执行操作并给出结果"），针对"复述下一步却不去做"的真实退化形态。检测逻辑（精确周期 + 工具循环）保持不变。
- **修复（预算重置）**：用户实测发现「3 次之后次数不重置」。根因：预算重置依赖布尔 `steerInFlight` 标记，一旦某条 steer 的 `message_start` 在 abort/自动续跑竞态中错位，标记卡死，之后任何真实用户回合都不再重置预算。修复：引入 `RetryBudget` 类，用**内容精确匹配**识别自己的 steer（Pi 投递 steer 用户消息时文本与发送时一致），真实用户消息才重置；去掉布尔标记，确定性、无竞态。单测覆盖：回合内 3 次封顶、真实用户消息重置、自身 steer 不重置、完整 steer 周期后重置。
- **实测修订（压缩续跑）**：用户实测发现无限循环主要出现在 deepseek-flash 且上下文较大（约 30%）时——这是**长上下文退化**（注意力稀释、丢失"已完成动作"的工作记忆），而 abort+steer 每次干预都会把垃圾留进上下文、反而加剧退化（自反馈）。修订：steer 预算耗尽后不再直接放弃，而是 `ctx.compact()` 压缩上下文、重置预算、发一条"继续"steer 重跑；每回合最多压缩续跑 1 次（`MAX_COMPACTION_RETRIES`），压缩失败或无预算时维持原放弃行为——保持 hard-capped 不变量。
- **实测修订（重试预算 3→2）**：将每次逻辑回合的 steer 预算由 3 收敛为 2——压缩续跑已经提供了第二次机会，收紧预算可减少"反复尝试→压缩"的轮次与上下文膨胀；末次措辞仍保留"放弃或说明卡点"兜底。`GUARD_STEER_MAX_RETRIES = 2`。
